# FAQ: Managing Dependencies Across Squads and Tribes

## How often should we rerun the dependency inventory?

Spotify's material says squads are asked about dependencies regularly but does not set a cadence. A practical choice is to tie the inventory to an existing rhythm, for example each planning cycle or each squad retrospective. Run it often enough that the board reflects current reality. If items on the board are routinely stale, the cadence is too slow.

## Who should attend an on-demand Scrum of Scrums?

One person from each affected squad, not whole squads. Choose the person closest to the dependency, which is often an engineer rather than a product owner. The Spotify material does not describe these representatives as a formal liaison role, so there is no need to appoint permanent attendees. Rotating by dependency keeps the meeting small and relevant.

## Should we aim for zero dependencies between squads?

No. The aim is squads that are as autonomous as possible, with removal effort focused on dependencies that block or slow delivery. Some collaboration between squads is how valuable things get built. Chasing zero usually produces duplicated capabilities or oversized squads, which create their own problems.

## What is the practical difference between a blocking and a slowing dependency?

A blocking dependency stops a squad from delivering in an area until another squad acts. A slowing dependency lets the squad proceed, but with delay, workarounds or rework. Blocking items should go first into removal discussions and, if needed, an on-demand sync. Slowing items can usually be logged and handled in normal planning.

## Does the dependency board need to be physical?

Spotify's described implementation used a board with sticky notes, but the point is visibility and a shared working list, not the medium. A digital board works if every affected squad actually looks at it. Keep the fields minimal so cards get updated. If squads maintain private lists alongside the board, the board is not doing its job.
