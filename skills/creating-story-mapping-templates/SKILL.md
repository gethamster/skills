# User Story Mapping Template: Build One Your Team Reuses

> Build a reusable user story mapping template for a wall, Miro, Mural or Google Sheets so every mapping session starts from the same structure.

Check whether this project has a `.hamster/` directory. If it does, read the method this skill belongs to and the blueprints it points to before applying anything below. ## Overview

A user story mapping template gives every session the same starting structure, so the group spends its time on the user's story and not on arranging the board. The structure itself comes from Jeff Patton's work. His [Story Mapping Quick Reference](https://jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf) names the parts a map needs: the users, with lightweight persona sketches; user tasks written as short verb phrases; activities that group tasks; a narrative flow from left to right; a backbone; details hanging below; and release slices marked with tape, each with its target outcomes on a card to the left. A good template has a place for each of these and nothing that gets in the way of moving cards.

There is no single official template. Whiteboard vendors publish their own versions: [Miro's user story map template](https://miro.com/templates/user-story-map/) comes set up with blank cards for activities, tasks and stories and lets you insert sections for releases, and [Mural's template](https://www.mural.co/templates/user-story-map), which credits Patton, walks through choosing a topic, mapping activities, detailing steps, mapping stories to steps and organizing releases. A wall with sticky notes and tape works just as well. This skill covers building a reusable story map template that fits your team, in whichever medium you use. For the method itself, see the [User Story Mapping](../../methods/story-mapping/METHOD.md) page.

A template earns its keep in three ways. It saves setup time at the start of every session. It makes maps from different teams readable to each other, because rows, colors and release lanes mean the same thing everywhere. And it carries small reminders, such as the outcome card beside each slice, that facilitators otherwise forget.

The risk is over-building. A template stuffed with example cards, fields and instructions slows the session down. Keep the structure light and let the content come from the room.

## How It Works

A story map template is a layout plus conventions. The layout sets rows and lanes. The conventions set what each card color and position means.

The rows follow the map's levels. At the top sit the brief and the user sketches, which the quick reference's Frame step puts first: what you are building, who it is for (including the "chooser" who buys it), and why. Below that comes the activity row, then the row of high-level user tasks, which together form the backbone. Below the backbone is open space for sub-tasks, alternatives, exceptions and details. The Nielsen Norman Group suggests assigning a different sticky-note color to each row so the map stays visually organized ([NN/g](https://www.nngroup.com/articles/user-story-mapping/)).

Release lanes run across the body. Patton describes using a long strip of masking tape to make "horizontal swim lanes for each release" and moving stories into each lane ([The New User Story Backlog is a Map](https://jpattonassociates.com/the-new-backlog/)). The quick reference adds an outcome card to the left of each slice. On a digital board, these become labelled horizontal sections that can be added, renamed and moved.

Each medium has its quirks. On a wall, cards and tape make moving things effortless, and Patton's original article has cards carry the same information in the same place every time, so they "start to look like playing cards in a game" ([How You Slice It](https://www.jpattonassociates.com/wp-content/uploads/2015/01/how_you_slice_it.pdf)). In Miro, the User Story Map app adds activity, task and story cards with keyboard shortcuts and a release control, and Jira cards can be dragged into releases; the help page notes that cards in the Tasks line cannot be converted into Jira cards ([Miro Help Center](https://help.miro.com/hc/en-us/articles/360020712554-User-story-mapping)). In Mural, the template provides the frame and you work with standard sticky notes. In a spreadsheet such as Google Sheets, columns become backbone tasks, rows become levels and release bands, and each cell holds one card; NN/g lists collaborative spreadsheets among the tools remote teams can map with.

Spreadsheets trade flexibility for structure. They are easy to share, filter and export, but moving a card means cutting and pasting, which discourages the rearranging that makes mapping useful. One workable arrangement is a whiteboard during sessions and a spreadsheet or backlog tool as the record afterward.

## Step-by-Step Guide

### Step 1: Choose the medium your sessions use

Pick the medium the team will actually map in: a physical wall, a whiteboard tool such as Miro or Mural, or a spreadsheet. Base the choice on where participants are and how much rearranging you expect. If sessions are hybrid, build the template in the digital tool so everyone works on the same board. You can keep a spreadsheet version as the record.

### Step 2: Lay out the frame and user areas

Reserve the top left for the brief, with three prompts: what, who and why. Next to it, add space for persona sketches with a name, a role, a goal and a line for the chooser. Keep these areas small so they stay visible without crowding the map. They remind the group whose story is being told.

### Step 3: Create the backbone rows

Add a labelled row for activities and a row for high-level user tasks below it. Set one card color for each row and use it consistently. Leave the rows empty, or add a single sample card showing the verb-phrase style, then remove the sample before the session. Mark the bottom of the backbone with a line so the body is clearly separate.

### Step 4: Add the body and release lanes

Below the backbone, leave open space for the details, and draw release lanes across it. Label the first lane for the first release and add at least one more for later work. Put an empty outcome card at the left edge of each lane with the prompt "What will users be able to do, and how will we know?" On digital boards, make the lanes easy to add, rename and resize.

### Step 5: Add a short legend

Include a small key showing what each card color means and any markers you use, such as a risk dot or a question tag. Keep it to a handful of entries so people can remember it. Put it in a corner where it will not be covered by cards.

### Step 6: Test the template with a real map

Use the template for a real session or rebuild a recent map in it. Watch where people hesitate or misplace cards, and note which parts they ignore. Remove anything nobody used and fix anything that confused people. A template that only its designer understands needs simplifying.

### Step 7: Publish it and keep it current

Save the template where every facilitator can find it, with a one-line note on when to use it. Name an owner who updates it when the team changes its conventions. Review it after several sessions and fold in anything facilitators keep adding by hand.

## Best Practices

- Mirror Patton's parts and nothing more. Users, backbone, body, release lanes and outcome cards cover what a session needs.
- Keep one color per level. Consistent colors let anyone read a map at a glance, which NN/g recommends for keeping maps organized.
- Put the outcome card in every lane. It keeps release debates focused on what users will be able to do.
- Leave the template empty. Example content anchors the group on someone else's product.
- Choose the medium for moving cards. Mapping depends on rearranging, so use the tool that makes that easiest during the session and export afterward.
- Version the template lightly. When the team changes a convention, update the template and note the change so older maps still make sense.

## Common Mistakes

- **Over-structuring the body**: Pre-drawn cells for every story constrain how deep a column can go. Leave the body open below the backbone.
- **Using a spreadsheet for the live session**: Cutting and pasting slows rearranging and discourages the conversation. Map on a wall or whiteboard and record in the spreadsheet.
- **No place for users**: A template without a persona area produces maps about nobody in particular. Keep users at the top.
- **Colors that change meaning between maps**: When a color means risk on one map and activity on another, maps become hard to compare. Fix the legend and reuse it.
- **Forgetting release outcomes**: Lanes with only a release name invite feature-list debates. Add the outcome prompt to every lane.
