# Examples: Prioritizing and Slicing Releases on a Story Map

## A first slice for an invoicing tool

**Scenario:**

Illustrative scenario: a small team has mapped an invoicing tool for freelancers. The backbone reads: set up my business, add a client, create an invoice, send it, get paid, see how I am doing.

**Walkthrough:**

The team arranges each column. Under "create an invoice," a single-line invoice sits at the top, with templates, recurring invoices and multiple currencies below. Under "get paid," marking an invoice as paid by hand sits above online card payments. The business owner draws the first line under the top card in every column except "see how I am doing." The group asks whether a freelancer can manage without reports, and agrees they can for now by exporting a list of invoices, which is a small card they add above the line.

The outcome card to the left of the slice reads: a freelancer can bill a client and record payment without leaving the tool. The measure is how many invoices early users send. Developers total their estimates for the slice and find it fits the time available, so the second line picks up online payments and reminders.

## Splitting a card that will not fit

**Scenario:**

Illustrative scenario: a team building a volunteer scheduling app believes "match volunteers to shifts automatically" is necessary for the first release, but developers estimate it as the largest card on the map.

**Walkthrough:**

The facilitator asks Patton's questions. Can coordinators do their work without it? Only with difficulty. Is there a manual workaround? Coordinators already assign shifts by hand in a spreadsheet. Can it be split into a crude version and an elaborate one? Yes: a list of available volunteers for each shift, sorted by availability, supports manual assignment. The crude version goes above the first line and automatic matching moves to a later slice.

## Phasing the first release

**Scenario:**

Illustrative scenario: a team has agreed the first release of a support ticket tool and wants to plan how to build it.

**Walkthrough:**

The opening game is a walking skeleton: a customer submits a ticket through a plain form, an agent sees it in a basic list, replies, and closes it. The team shows this to a few agents as soon as it works. The mid game adds ticket assignment, email notifications and search. The end game covers polish, performance checks and the gaps agents raised. Each phase has a short outcome statement on the map, so progress can be judged by what users can do.
