# Event Design

## Naming

### Event names: Title Case, Object-Action

```
Right:   'Brief Created'
         'Routine Triggered'
         'Subscription Updated'

Wrong:   'brief_created'        (snake_case for events — no)
         'briefCreated'         (camelCase — no)
         'Create Brief'         (verb first — no)
         'User Created Brief'   (subject in event name — no, that lives in properties)
```

The subject is always the event's actor; never include it in the event name. Use `user_id` and `account_id` properties to identify the actor.

### Property names: snake_case

```
Right:   { brief_id, account_id, user_id, creation_method }
Wrong:   { briefId, accountId, userId, creationMethod }
```

### IDs always include the type

```
Right:   { brief_id, task_id, account_id, routine_id }
Wrong:   { id, parent_id, target }
```

### Booleans start with `is_`, `has_`, or `was_`

```
Right:   { is_first_run, has_initial_content, was_auto_generated }
Wrong:   { firstRun, initial_content, autoGenerated }
```

### Counts end with `_count`, durations with `_ms` / `_seconds` / `_hours`

```
Right:   { task_count, response_time_ms, completion_time_hours }
Wrong:   { tasks, responseTime, duration }
```

## Required Properties

Every server-side event must include:

| Property | Type | Why |
| --- | --- | --- |
| `account_id` | `string` (UUID) | Group analytics requires it |
| `user_id` | `string` (UUID) | Per-user analysis; `userId` arg sets distinct ID, prop sets queryable filter |

The third argument to `trackServerEvent` is `userId` and sets the PostHog `distinctId`. Pass it AND include `user_id` in properties.

```typescript
trackServerEvent(
  'Brief Created',
  {
    brief_id: brief.id,
    account_id: accountId,   // required
    user_id: userId,         // required (for queries)
    has_initial_content: true,
  },
  userId,                    // required (sets distinctId)
);
```

## Property Types

Use `EventPropertiesMap` for compile-time safety:

```typescript
import type { EventPropertiesMap } from '@kit/analytics';

type BriefCreated = EventPropertiesMap['Brief Created'];

const props: BriefCreated = {
  brief_id: brief.id,
  account_id: accountId,
  has_initial_content: true,
};
```

If your event is not in `EventPropertiesMap`, **add it before merging**. Untyped events accumulate as tech debt.

## State Sync (`$set`, `$set_once`, `$groups`)

Mutate user/group properties on the *same* event that triggers the change. Do not fire a separate `identify` round trip.

### `$set` — overwrite every time

```typescript
trackServerEvent('Routine Triggered', {
  routine_id, account_id, user_id,
  $set: {
    last_routine_run_at: new Date().toISOString(),
    last_active_at: new Date().toISOString(),
  },
}, userId);
```

### `$set_once` — set on first occurrence only

```typescript
trackServerEvent('Routine Triggered', {
  routine_id, account_id, user_id,
  $set_once: {
    first_routine_run_at: new Date().toISOString(),
  },
}, userId);
```

### `$groups` — usually unnecessary (auto-injected)

`$groups: { account: account_id }` is auto-injected by `trackServerEvent` from RequestContext. Only set it manually if you are tracking from a context where the request middleware did not bind the account (e.g. cross-account admin actions).

## Feature Adoption Pattern

When shipping a new feature surface, the plan must include:

1. **Add to `UserProperties`** in `packages/analytics/src/user-properties.ts`:

```typescript
has_used_routines?: boolean;
   routine_count?: number;
```

1. **Extend the unions** in `user-trait-manager.ts`:

```typescript
markFeatureAdoption(userId, 'routines')
   incrementEngagementCounter(userId, 'routine_count')
```

1. **Wire on first use** (server-side, idempotent):

```typescript
await markFeatureAdoption(userId, 'routines');
   await incrementEngagementCounter(userId, 'routine_count');
```

1. **Fire a milestone event** the first time:

```typescript
if (count === 1) {
     trackServerEvent('First Routine Created', {
       user_id: userId,
       account_id: accountId,
       feature_id: 'routines',
       time_since_signup_hours: hoursSinceSignup,
     }, userId);
   }
```

## Common Failure Modes

### Untyped string-soup events

```typescript
// Bad — typo-prone, untyped, no autocomplete
trackServerEvent('routine_triggred', { ... }, userId);
```

Fix: add to `EventPropertiesMap`, use `EventPropertiesMap['Routine Triggered']`.

### Missing `account_id`

```typescript
// Bad — group analytics breaks; cannot filter by workspace
trackServerEvent('Brief Created', { brief_id, user_id }, userId);
```

### Mixing concerns in one event

```typescript
// Bad — one mega-event for everything that happens in a flow
trackServerEvent('Brief Flow', { step, action, target, ... });
```

Fix: one event per outcome. Multiple atomic events are easier to query than one with a `step` discriminator.

### High-cardinality property values

```typescript
// Bad — every URL is unique, makes funnels useless
trackServerEvent('Page Viewed', { url: req.url });
```

Fix: bucketed properties — `route_pattern: '/briefs/:id'`, not the literal URL.

### Stamping PII without `_pii` suffix

```typescript
// Bad — fails the PII boundary check
trackServerEvent('Invite Sent', { invitee_email: '...' });
```

Fix: rename to `invitee_email_pii` so it is grep-able and explicit.
