# FAQ: How to Build a Minimum Viable Product (MVP)

## How do I know my MVP is small enough?

Check each feature against the core flow. If removing it would stop a customer from completing the task the assumption depends on, keep it. If removing it only makes the product less complete or less polished, cut it. A useful sign is that the team feels slightly uncomfortable shipping it.

## What are the minimum viable product steps in order?

Name the assumption, map the core flow, freeze the feature list, pick the cheapest build approach, instrument, launch to a defined audience, compare the result with the pass mark and record the decision. The order matters because each step narrows the next. Teams that start at the build step usually end up with a small first release rather than an experiment.

## Should the MVP be built with code?

Only where nothing cheaper will deliver the core flow. Many MVPs are delivered by hand, stitched together from existing tools, or built with no-code builders. Code is worth writing when manual delivery becomes the bottleneck or when the assumption is about the technology itself.

## How long should an MVP test run?

Long enough for the behavior you measure to happen more than once. A one-time action such as a sign-up can be read quickly, while a habit such as weekly use needs several weeks. Decide the window before launch and do not extend it because the numbers are unclear. An unclear result after a fair test is itself something to record.

## What happens to the MVP after the test?

The learning is kept even when the product is thrown away. Some MVPs grow into the first release, and many are replaced once the assumption is confirmed. Decide based on what the next test needs, and avoid carrying rough code into production just because it exists.
