# FAQ: Implementing Frequent Delivery Cycles in Crystal Projects

## How often should a Crystal team deliver?

There is no single mandated interval. Cockburn's Crystal presentation says every month or two, while the [Cooperative Game handout](https://uxhh.de/roundtable/archiv/_media/2008/HO08-21_CockburnAlistairASD.pdf) says every two to four months. Deliver as often as you can produce genuinely usable, tested software, and never let the interval grow past the point where feedback still changes decisions.

## What counts as a delivery in Crystal?

A delivery is running, tested, usable functionality that users actually operate. The [Crystal Clear review](https://developerdotstar.com/mag/bookreviews/cockburn_crystal_clear.html) and [practitioner guidance](https://projectmanagementformula.com/crystal-agile-methodology) both exclude demonstrations, prototypes and builds that merely compile. If a user has not used it, treat the cycle as not yet delivered.

## What if our client cannot accept incremental releases?

Cockburn's answer, reported in the [Crystal Clear review](https://developerdotstar.com/mag/bookreviews/cockburn_crystal_clear.html), is to deploy to a test workstation where a friendly user can try the increment. If even that is impossible, hold user viewings that give users ample opportunity to see work in progress. Use the highest option your constraints allow and revisit the constraint regularly.

## Is a Crystal delivery cycle the same as a Scrum sprint?

It is a different emphasis. A Crystal cycle is judged by whether usable software reached real users, and [practitioner guidance](https://projectmanagementformula.com/crystal-agile-methodology) says its length should come from project context rather than a standard duration. For the broader comparison between Crystal and other methods, see the [Crystal Agile Framework](https://tryhamster.com/methods/crystal-agile-framework) page.

## How can we check whether we are delivering frequently enough?

Cockburn's own checklist, reproduced in an [Agile 2007 session document](https://scribd.com/document/95144672/Agile-2007), asks whether the team has delivered running, tested, usable functions to its user community at least twice in the last six months. Treat that as a floor, not a target. A second check is whether feedback from the last delivery actually changed the current plan.
