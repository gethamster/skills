# FAQ: Running Inspect and Adapt Workshops

## When should the Inspect and Adapt event be held?

Hold it at the end of each Program Increment. SAFe's glossary places I&A there, as the point where the current state of the solution is demonstrated and evaluated. Holding it just before the next PI Planning is practical because the improvement items flow straight into planning while they are fresh.

## Who should attend Inspect and Adapt?

Invite the whole train where possible: team members, product management, system architects, the RTE and business owners. The problem-solving workshop works best with mixed groups, because many root causes span teams and roles. If the train is very large, send representatives to the workshop but keep the demo and measurement review open to everyone.

## What measures should we review?

Start with business value planned versus achieved against the PI objectives, since those were the train's explicit commitments. Add a small set of flow, quality and operational measures you already collect, rather than inventing new ones for the event. Where the train measures the results of release hypotheses, include them, because they show whether delivered work produced the value expected.

## How is the I&A system demo different from iteration demos?

Iteration demos usually show one team's work at the end of each iteration. The I&A demo shows the integrated solution across the whole train, organised around PI objectives rather than team boundaries. Its purpose is evaluation of the solution's current state, so gaps and integration problems are findings, not embarrassments.

## How many improvement items should we commit to?

Commit to only as many as the train can realistically finish in the next PI alongside feature work, for example two to four. Each needs one named owner, acceptance criteria and a size so it can be planned like other backlog items. A short list that gets done is worth far more than a long list that erodes trust in the event.
