# FAQ: Integrating Expert User Access into Development Workflow

## What counts as an expert user in Crystal?

An expert user is someone who does the work in the project's domain and can answer questions and suggest solutions. Crystal guidance is clear that this should be a real-life user rather than a tester from the development team. Domain analysts and product managers can support the relationship, but they do not replace first-hand experience of the job.

## How much of the expert's time do we need?

The sources describe access as regular and continuous rather than setting a fixed number of hours. In practice, short latency matters more than total time, so a small daily availability for quick questions usually beats a long monthly session. Start with something modest, for example one short working session a week plus same-day answers, and adjust in reflection workshops.

## Can the product manager act as the expert user?

Only if the product manager actually does the work the software supports, which is rare. A product manager's view of users is second-hand, filtered through interviews and data. Their job in this practice is to secure the real expert, keep the channel healthy and make sure feedback reaches the plan.

## What if no real user can commit time to the project?

Treat it as a risk to raise with sponsors, since Crystal lists expert access as a core property rather than an extra. Negotiate a smaller but regular commitment instead of accepting none, and make the ask concrete by showing the questions currently being guessed. Record the gap explicitly so decisions made without expert input are flagged for later validation.

## How do we know the practice is working?

Look for three signals: developers get domain answers quickly, the expert has used the current build, and recent backlog or acceptance-criteria changes trace back to expert input. If questions queue up, the expert only sees demos, or feedback never changes the plan, the loop has broken. Review these signals in each reflection workshop.
