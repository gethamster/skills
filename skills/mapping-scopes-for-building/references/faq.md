# FAQ: Mapping Shape Up Scopes Instead of Tasks

## What is a scope in Shape Up?

A scope is a part of a project that can be built, integrated and finished independently of the rest. It groups the design and programming tasks for one meaningful piece of the product, such as Locate or Reply in the book's message drafts example. Scopes are bigger than tasks, much smaller than the whole project, and usually finishable in a few days or less.

## When should a team map its scopes?

After it has done some real work. The book expects accurate scopes around the end of the first week or the start of the second, once the team has seen how the parts of the problem connect. Ryan Singer's later practice with other companies drafts vertical slices at kickoff from the breadboard, but the team still refines them as it learns.

## How many scopes should a project have?

The book does not give a number; it asks that you can see the whole project and that each scope is small enough to finish soon. In his recent case study, Singer says he breaks the work into at most nine scopes. If you have many more, some are probably tasks; if you have only one or two, important problems may be hiding inside them.

## Where do bugs go?

File each bug under the scope it affects. The book calls a generic bugs list a junk drawer, because it prevents you from ever knowing whether a given scope is really done. QA findings start as nice-to-haves and move into a scope's must-haves only when the team decides they matter.

## What is the Chowder list?

A list for loose tasks that do not fit any scope. The book allows it but says to keep a skeptical eye on it: if it grows past three to five items, there is probably a scope to be drawn. Keep it off the hill chart.

## How is a scope different from a user story or an epic?

A scope is discovered by the team during the build and defined by what can be finished independently in this particular codebase. User stories and epics are usually written before the work starts, often by someone other than the builders. Scopes also always integrate front-end and back-end work, so finishing one produces something that can be demonstrated.
